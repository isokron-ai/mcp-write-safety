# 0003. The durable store is a JSONL journal of committed post-state (`journal-format/1`)

- Status: accepted (16 Nov 2026; owner decision 2)
- Applies from: 0.3.0 (feature `durable`, needs `--data-dir`)

## Context

A delayed-recovery check (24 hours) should not depend on one process staying up. The store has to survive a restart, and a restart must not change anything a digest covers. Node's built-in SQLite module is still experimental on the Node 22 line, and tiny-tracker supports Node 22.12 and later with one runtime dependency.

## Decision

1. **One JSONL journal** in the data dir. The first line is a header: `{"jseq":0,"line":"header","journal":"journal-format/1","writer":"<package version>","boot_id":…,"seed":{…}}`. The seed (the seeded projects as created, and the id counters) lives in the header, so a restart keeps the seed's `created_at`.
2. **Post-state only, never commands.** A line records what a transaction committed: ids, versions, timestamps and the id counters as committed, the operation record and the execution record. Replaying a journal never calls the clock or re-runs an operation, so a restart cannot change a digest.
3. **One line per transaction.** The effect, its key record and its execution record are in the same line, so the "same transaction" of the idempotency pattern is literal and readable. Each line carries its own line number `jseq` (0 for the header, contiguous) and a checksum; a commit line also carries `commit_seq`, the store's commit sequence (the execution record's `seq`), which is not derived from the line's position. Line shapes: `docs/INTERFACES.md` 1.9. The answer is sent only after the line is flushed (`fsync`). On macOS, Node's `fsync` is not `F_FULLFSYNC`, so a flushed line survives a process crash but not necessarily a power cut; the backend logs this at start there (G2 fold-in 13).
4. **Commits stay synchronous.** Where a write has a pending state, the pending line is written first; the commit is one synchronous section after it. Conditional writes and batches are one section each.
5. **Recovery:** a torn write is tolerated: an unterminated last line that does not decode is left out (and logged), and from 0.4.0 so is such a fragment once a later write has joined it on its physical line (below). A bad line anywhere else, or a last line that has its newline or decodes with a problem, stops the start with an error and the file is not touched (G2 fold-in 3). A pending line with no commit becomes `aborted` (an `aborted` line naming it by `pending_jseq`, reason `orphan_at_start`): nothing was applied. A pending line whose run a later commit line reset, with no fence line for it, is fenced at start instead (its fence line written then; G2 fold-in 5).
   - **Nothing is cut (0.4.0, G3 note 26 item 1a; replaces the seams v2.1 truncate).** 0.3.0 cut the file back after a failed append, and cut a torn last line at start. Both cuts are a check followed by an act on a shared file: a holder paused between them, past a takeover, would cut the new holder's acknowledged lines. From 0.4.0 the journal is open `O_APPEND` and written with no position, and nothing is cut once the lease is taken. An append that fails before its write begins leaves the journal usable; one that fails once its write has begun marks it broken (every later write answers 503; restart it). That request is answered 503 `journal_unavailable` with its outcome unknown: a whole line (the write finished, the flush failed) is applied by the next start, a torn one is left out. It keeps the code `journal_unavailable` rather than a new one, and its message says the outcome is unknown; `journal_unavailable` as a code means "not applied here", not "never applied". A torn write stays in the file; the next write joins it on its physical line, and every reader leaves the fragment out: the whole line is the longest suffix that starts with `{"jseq":` and whose checksum holds. `jseq` stays contiguous over the applied lines, so a fragment can never hide an applied line; a physical line with no whole line in it, other than the last, is refused as before.
   - Aborted lines carry a reason: `refused`, `journal_unavailable`, `fault`, `internal_error` or `orphan_at_start`.
6. **Fences and runs are journalled (seams v2.1).**
   - A run reset that fences a pending key record writes a `fence` line (`principal`, `key`, `run`, `pending_jseq`, `reset_seq`) after the reset's commit line. It ends that pending line (no `aborted` line), and at load it restores the fence, so the key stays refused (409 `key_fenced`) after a restart.
   - **Fenced keys never expire** (owner decision, 16 Nov 2026). A fence lasts for the life of the data dir, like a tombstone: key retention (decision 0004) does not remove it, and a fenced key is never reusable. A write in flight when its run was reset can therefore never land later under that key, across any restart.
   - Allocating a run writes a `run-alloc` line (`run_id`, `principal`, `created_at`, `label`) before the run is answered; at load the run registry is rebuilt from these lines, so run-ownership checks (403 `run_not_owned`, `run_not_allocated`) hold after a `--supervise` restart.
   - A settle-by-lookup fence (a lookup that found no record closed the key) writes an additive `lookup-fence` line before it answers, so a late original cannot land after a restart (0.3.0 integration). The format stays `journal-format/1`: this version's reader knows the kind, and an older reader refuses a journal with a kind it does not know rather than skipping a fence.
   - A fixture clock move (`POST /_fixture/clock`, feature `clock`) writes an additive `clock` line (`from_ms`, `to_ms`, `at`) once the offset is stored and before it is answered, putting the offset back if the line fails (0.4.0, coordinator note 19; order from G3 note 26 item 5, so a store that cannot keep the offset never leaves a line ahead of the answer; an offset kept ahead of the journal, after a crash between the two under `--supervise`, gets its line at the next start); at load the clock's offset is set to the last line's `to_ms`, forward only, before anything is served. A journal with clock lines refuses to load without the `clock` feature, since on wall time its record time would move back. This retires CMP-65 (0.3.0 refused `durable` with `clock`).
   - None of them takes a commit sequence.
7. **`durable` requires `strict-input`** (compat rule CMP-50): every line is checksummed over RFC 8785 bytes, which a string with a lone surrogate does not have, so such input is refused at the door instead of failing the journal append.
8. **One process per data dir.** A lease (0.4.0, below) and a pid lock refuse a second writer, including a stale child next to its supervisor. More than one server instance is a non-goal.
9. The data dir is created `0700`; a directory that is not empty and was not created by tiny-tracker is refused.

## Consequences

- A whole-stack restart keeps data, key records and digests; delayed recovery no longer needs a pinned process.
- The journal is readable with standard tools, and a third party can recount effects from it.
- The journal format has its own version, separate from the package version and from `fixture-api`.

## The data-dir lock (G2 round 3)

The lock is best-effort, as G13 allows ("one instance, enforced best-effort"): Node core has no OS-held lock. A stale lock is taken over by rename-aside, compare (same inode and text) and link-back, and a takeover never deletes a moved lock it has not proven stale; a live lock can still be moved, or, in the three-starter window below, deleted (a clean close that has checked its lock, then a move-aside and a third start's link before its unlink). Two residual cases are stated, not fixed: a starter that crashes or stalls between the move and the link-back can leave the holder without a lock file; and three simultaneous starts can leave two running (the second refuses and keeps the moved lock). The mitigation is one starter per data dir (`--supervise` serializes its children). 0.4.0 adopts an OS-held lock: a native helper, mkdir leases with heartbeats, or the supervisor as the only starter.

## The data-dir lease (0.4.0, coordinator note 19 item 11)

The 0.4.0 adoption is an mkdir lease with a heartbeat (the proper-lockfile pattern), with no runtime dependency and no native build: a native helper (flock/LockFileEx) would add a compiled dependency to a zero-dependency package, and "the supervisor as the only starter" does not cover `all` without `--supervise`, stdio or the container.

- **The lease** is the directory `lock.d` with an `owner` file (`pid`, `host`, `nonce`). It is created whole: a private temp directory gets the owner file, flushed, then is renamed to `lock.d`; the rename fails while a `lock.d` exists (it is never empty), so exactly one starter gets it. The holder refreshes its mtime every 2 s.
- **Stale:** a heartbeat more than 20 s old; or, on the same host only, a gone pid, or this pid with a text this process did not write (a container's pid 1). A pid on another host is never looked up. The takeover is a compare-and-rename: looked at again right before the move, moved aside, removed only if the moved directory has the inode, owner text and mtime that were judged stale; otherwise put back into a free name, or left aside and the start refuses.
- **The fence:** before every journal append the holder checks that `lock.d` is still its own (inode and owner text; a missing one is looked at again for up to 50 ms, the time a starter takes to put back a lease it moved by mistake) and that its last heartbeat is less than 10 s old. Otherwise the lease is lost for good: the append throws, writes answer 503 `journal_unavailable`, and the process must be restarted. The 10 s self-fence is under the 20 s stale time, so a holder stops appending before any other start may judge its lease stale.
- **The check and the write are not atomic** (G3 note 26 item 1, reviewer A's MUST FIX; the earlier text here claimed this window closed). A holder paused between its check and its write, for longer than the stale time, writes one more line after another start took the lease over. 0.4.0 makes that line lose cleanly, with a fencing token in the file:
  - the file is open `O_APPEND`, so the late line goes after the new holder's lines, never over them, and nothing is cut (above);
  - each start writes a `lease` line with an epoch one more than the highest in the file, before it replays; every line carries its writer's `epoch`; at replay a line of a lower epoch after a lease line, or appended after the new holder read the file (its `jseq` at or above the lease line's), is **superseded**: not applied, reported and logged;
  - after the flush the holder checks the lease again; if it was taken over, the request is answered **503 `lease_lost`: the outcome is unknown**. It is not "dropped at replay": a line that reached the file before the new holder read it is applied by the new holder. A keyed repeat to the new holder settles it (a replay, or one application). The paused holder never answers success for a line the new holder may not have.
- **A long load keeps the lease** (G3 note 26 item 3): the load beats the lease while it reads and replays (the heartbeat timer cannot run during a synchronous load) and checks ownership and beats again before its first append.
- **Hosts** (G3 note 26 items 4 and 5): the pid lock names its host, and a pid lock written on another host is judged by the lease alone; any takeover by age takes the old holder's pid lock with the lease, whatever host it ran on. A lease naming another hostname whose heartbeat is older than the 10 s self-fence time is stale at once (that holder, wherever it runs, has stopped appending by its own rule): `docker run --rm --init` gets a new hostname each run, so a restart after an unclean stop waits up to 10 s (with `--hostname`, the gone-pid rule makes it immediate). On a shared hostname the gone-pid rule takes over a lease whose pid this process cannot see, whichever pid it is. Data safety across clock skew between hosts rests on the epochs, not on the times. A lease folder that cannot be moved or removed (EPERM, EBUSY, EACCES or ENOTEMPTY, as on Windows) is a clear refusal: start again.
- **Remaining cases**, each failing closed (no acknowledged line is lost, none is answered as a success it is not):
  - a start whose lease is taken over between its read and its lease line, and two starts writing lease lines of one epoch: the start whose lease line is not the journal's last applied line refuses to start (its lease line, of an epoch not above the current one, is superseded); the next start goes on;
  - a start that found the file empty and lost the race: its header and lease line (one write) land after the winner's lines; it refuses, and they are superseded;
  - a holder whose append is cut short (disk full) leaves a fragment; the next line joins it and applies (above). A torn write whose fragment is joined by a line of a superseded holder is left out with it;
  - a journal with `lease` lines cannot be read by 0.3.0 (an unknown kind, refused, as with `clock` lines): no downgrade.
- **The pid lock stays as a second check** for 0.4.0 and is then retired. A start that took a lease over from a live process on this host (stopped beating: paused or hung) may take over that process's pid lock too, since the lease fences it.
- **What this closes:** the 0.3.0 residual cases (a starter that stalls between moving a lock aside and putting it back; three simultaneous starts) can still leave two processes running, but only the lease holder appends; the other is fenced at its next append. The remaining cost is availability: a holder fenced by such a race or by a pause refuses writes until restarted.
- **Tests (T1):** a killed holder (taken over by its gone pid), a paused holder (SIGSTOP past the stale time: the new start takes over, the resumed holder appends nothing), a holder paused past its self-fence time with no takeover, a holder paused between its lease check and its commit or pending line (the reviewer's probe: its client gets 503 `lease_lost`, the new holder's acknowledged writes survive a restart) and one whose continued write then fails (nothing is cut), two and three racing starts (fresh and over a killed holder's lease), another host's lease, a moved lease, the leftover sweep. SIGSTOP is skipped on Windows. `test/journal-epoch.test.ts` covers the epoch rules, joined fragments, the races of the remaining cases, a long load, the pid lock across hosts and the Windows refusals in process.
