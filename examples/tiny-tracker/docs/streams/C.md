## Running the lost-response contract

Our adapter for the shared lost-response test contract lives in `harness/adapters/tiny_tracker.py`, pinned to the contract at `92bf1ba5f8226a67409fd8a7a68411b5c4a7258d` (`harness/contract.json`). It needs only the Python standard library.

```sh
umask 077; mkdir -p ~/.tt-tokens
TRACKER_BACKEND_TOKEN=... node dist/src/cli.js all --features evidence,execution-records,lookup,ledger,faults \
    --fixture-control --token-dir ~/.tt-tokens | head -1 > state.json &
python3 -I harness/adapter_config.py --state state.json > config.tiny-tracker.json
# in a checkout of the contract at the pinned commit, with harness/adapters/tiny_tracker.py copied into fixtures/harness/adapters/:
python3 lost_response.py --config config.tiny-tracker.json --out ../../runs/<dir>
# or, from here, without changing the contract checkout:
python3 -I harness/selfcheck.py --config config.tiny-tracker.json --driver /path/to/contract
```

- **The counter** is the execution ledger: one `execution` entry per committed write, attributed by the operation tag the adapter sends in request `_meta` (the driver's session identity), whether or not the build forwarded the key.
- **The lost response** is server-side: the adapter arms `mcp/after-backend-reply/drop` for exactly the tool and key, once, on the control listener. Without a control listener it discards the answer client-side, as 0.1.0 runs did.
- **Digests.** A record serves exactly one digest, `result_digest`. The adapter recomputes it from the served canonical bytes with the domain tag (SHA-256 over the domain, a line feed and the bytes; decision 0002). A bare SHA-256 of the bytes does not match, by design.
- **Recovery by key alone** goes through `get_operation` in a fresh MCP session with no run tag. The A5 delayed leg reads `GET /operations/<K>`.
- **Self-attested.** The contract driver at the pinned commit takes the committed digest as the recovered digest when an attempt says `found`, without comparing them. Until it compares, the A3 key-only result rests on our adapter's classification, and we label it self-attested. The adapter reports the digest it recovered; `harness/selfcheck.py` compares it with the committed digest.

## fx-check

`fx-check` checks a running fixture's FX- properties from outside, through the evidence API, the way another harness would.

```sh
TRACKER_EVIDENCE_TOKEN_FILE=~/.tt-tokens/evidence.token TRACKER_BACKEND_TOKEN=... \
  node dist/src/fx-check.js --backend http://127.0.0.1:4601 --mcp http://127.0.0.1:4600/mcp --control http://127.0.0.1:4602
```

- Each property gets one answer: `held`, `violated`, `not checked` (with the reason) or `not applicable` (the build does not run the feature it needs).
- To probe, it writes a few tickets titled `fx-check probe ...` under its own keys, in a run of its own, and resets that run at the end. `--passive` writes nothing.
- FX-LOOK-3 needs a second principal's token in `FX_CHECK_SECOND_TOKEN`.
- Exit codes: 0 when nothing is violated, 1 when a property is violated, 2 when the setup cannot be used.

## Known answers

`expected/<version>.json` ([schema](../../schemas/expected-1.schema.json)) is generated by `expected/generate.mjs` from running each build in `expected/builds-<version>.json`, never written by hand. Each build's answers are keyed by its `build_hash` and given as sets:

- the FX- answers of `fx-check`;
- the contract driver's own verdict strings for LRT-A1 to A5 (`--contract-dir`, a checkout at the pinned commit);
- `mcp-writecheck demo`'s verdicts per requirement (`--writecheck`).

`--repeat N` merges N runs. `--check` regenerates and compares with the committed file byte for byte.

## Recounting from published files

`verify/python/tt_recount.py` recounts from the files a run publishes, with the Python standard library only:

- the execution ids and the count per (principal, run, operation tag, key), from the ledger, the execution records and, from 0.3.0, the journal;
- the tickets and comments the recorded writes leave behind, against the export;
- every served digest.

It exits 1 on any disagreement and names it. `--operation TAG --key K` prints the contract's count for one operation.
