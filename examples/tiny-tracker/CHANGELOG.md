# Changelog

All notable changes to `@mcp-write-safety/tiny-tracker`, the sample server for the MCP Write-Safety Requirements. The format follows Keep a Changelog; versions follow Semantic Versioning once published.

### Stream F (0.4.0 contract kit)

- `Dockerfile`, a public CI workflow (Linux, macOS, Windows; Node 22 and 24; known-answer reproducibility; the container), `CONTRIBUTING.md`, `docs/STABILITY.md`, `docs/patterns.md` and `openapi.yaml` for the backend, evidence and control APIs.

### 0.4.0 G3 review: the lease and the journal (reviewer A, coordinator note 26 items 1, 3, 4 and 5)
- **A holder paused past a takeover no longer overwrites the new holder's lines** (item 1, the MUST FIX). The journal is open `O_APPEND` and written with no position, so a late line goes after the new holder's lines, never over them. Nothing is ever cut from the file once the lease is taken, at load included (a start paused between a check and a cut could otherwise cut a newer holder's lines): a failed append that had begun marks the journal broken (every later write answers 503; restart it), and a torn write stays in the file, where the next write joins it on its physical line and every reader leaves the fragment out (`jseq` stays contiguous over the applied lines, so a fragment can never hide one). A new journal's header goes in the same write as its lease line.
- **Lease epochs** (additive to `journal-format/1`). Each start writes a `lease` line (`epoch`, `pid`, `host`, `nonce`) with an epoch one more than the highest in the file, before it replays; every line a writer appends after it carries its `epoch` (run-alloc and lookup-fence lines too). At replay a line whose epoch is lower than a lease line before it is a superseded writer's: it is not applied, the load report lists it and the start logs it. A journal written before 0.4.0 has no epochs and counts as epoch 0. A line with no epoch after a lease line, or with an epoch no lease line took, is refused.
- **`lease_lost` (503): the outcome is unknown.** After the flush the holder checks the lease again; if it was taken over meanwhile, the request is answered 503 `lease_lost`, never a success. This means "outcome unknown", not "dropped at replay": a line that reached the file before the new holder read it is applied by the new holder, and one that came later is not. A keyed repeat to the new holder settles which (a replay, or one application). The run, clock and fence routes answer `lease_lost` the same way. The ledger still records the refusal as `journal_unavailable` (its schema is unchanged).
- A long load keeps the lease (item 3): the load beats the lease while it reads and replays, and checks ownership and beats again after the replay, before its first append, so a replay longer than the stale time neither fences a healthy server nor lets another start take the lease.
- The pid lock across hosts (item 4): the pid lock names its host; a pid lock another host wrote is judged by the lease alone, and any takeover by age (any host) takes the old holder's pid lock with its lease.
- Availability (item 5): a lease naming another hostname whose heartbeat is older than the 10 s self-fence time is taken over at once (`docker run --rm --init` gets a new hostname each run; `--hostname` makes a restart immediate). A lease folder that cannot be moved or removed (EPERM, EBUSY, EACCES or ENOTEMPTY, as on Windows) is a clear refusal. The fixture clock stores a move's offset first and writes its `clock` line after, rolling the offset back if the line fails; an offset kept ahead of the journal (a crash between the two under `--supervise`) gets its `clock` line at the next start, before anything is served.
- `tt_recount.py` knows the `lease` kind, the epoch rules and joined fragments. A 0.3.0 reader refuses a journal with `lease` lines (an unknown kind), as with `clock` lines: the journal cannot go back to 0.3.0.

### 0.4.0 integration pass (g3a and g3b merged; on the 0.3.0 release)
- An append that fails once its write has begun is answered 503 `journal_unavailable` with its outcome unknown, as `lease_lost` is: the line may be in the file and the next start decides it. The code stays `journal_unavailable` (the ledger's schema is unchanged; the MCP layer answers every backend 5xx as outcome `unknown`), and the fence, run and clock routes no longer say "nothing was fenced" or "the clock did not move" for it. INTERFACES, decision 0003, FIXTURE and `openapi.yaml` say that `journal_unavailable` means "not applied by this process", never "never applied".
- `fx-check` FX-DUR-2 reads a journal line that a later write joined onto a torn fragment (0.4.0 never cuts the file): it takes the line's whole part, as the server's reader does, instead of skipping the physical line.
- Racing starts over a killed holder's lease: a start whose new lease could not be renamed into place because a lease was there (ENOTEMPTY or EEXIST) looks again, even if another start has moved that lease aside meanwhile. It was refused with a message for a Windows file lock (and before 0.4.0's Windows mapping, with a raw ENOTEMPTY error).
- The 0.4.0 matrix (coordinator note 26 item 7): the Lv level runs with the fixture clock, and the selector places `key-expires-early` only on a level with the clock (a matrix-only need, `MATRIX_NEEDS` in `expected/select-0.4.0.mjs`; the CLI still allows the defect without it). 515 builds cover 1043 pairs (4089 legal candidates); FX-KEY-1 detects `key-expires-early` on all 51 of its rows (it was 2) and is checked on every Lv row.
- CONTRIBUTING and STABILITY: a release's known answers reproduce at its own tag (`expected/0.3.0.json` at `tiny-tracker-v0.3.0`); a release regenerates and checks only its own file.

### 0.4.0 additions (coordinator note 19)
- The fixture clock with `durable`: each clock move is an additive journal `clock` line (`from_ms`, `to_ms`, `at`), written before the offset is stored; the offset is restored at load, and a data dir with clock lines refuses to start without the `clock` feature. CMP-65 (`durable` with `clock` refused) is retired, and the 0.4.0 matrix's durable level runs with the fixture clock, so FX-KEY-1 is checked on durable rows. `tt_recount.py` knows the kind. `fx-check` makes the FX-DUR-1 plant after FX-KEY-1's clock move, so the restart measures durability only.

Before every journal append the holder checks it still owns the lease and beat within 10 s; otherwise it is fenced (writes answer 503 `journal_unavailable`; restart it). The 0.3.0 pid lock stays as a second check for this release. `fx-check` FX-DUR-2 counts `lock.d` among the data dir's files.

- `expected/builds-0.3.0.json`, `expected/0.3.0.json` and `expected/0.3.0.md`: the 0.2.0 builds, now with `inflight` and `retention`, plus `in-progress-reported-not-applied`, `settle-miss-reported-not-applied`, `key-expires-early` and a build with the fixture clock, generated by `expected/generate.mjs` (three runs each, with the contract driver at `92bf1ba` and `mcp-writecheck demo`). The known-answer files say so in `not_detected`.

### Stream D (0.3.0 durability)
- Feature `durable` with `--data-dir`: a JSONL journal of committed post-state (`journal-format/1`: `jseq` and an RFC 8785 checksum on every line, the seed in the header), flushed before every answer and replayed with no clock read; a torn last line is dropped, any other bad line stops the start; a pid lock allows one writer per data dir; the data dir is private (0700).
- Feature `inflight`: a pending key record before the commit section; a same-key call meanwhile answers `in_progress` (outcome `unknown`, repeat `same_key`); a key fence for settle-by-lookup (`POST /operations/:key/fence`).
- Feature `retention`: keys remembered for 7 days (`--key-retention`), stated in every key-accepting tool; `--key-expiry refuse` (tombstones: an expired key with the same request is answered applied, with its execution id) or `forget`.
- Variants `key-store-durable`, `settle-by-lookup`, `settle-by-client-reference`. Defects `in-progress-reported-not-applied`, `settle-miss-reported-not-applied` (need `inflight`); backend defects `key-record-not-durable`, `key-record-after-effect`, `key-expires-early`. Compatibility rules CMP-51 to CMP-54 (CMP-50 at the integration).

### Stream E
- Feature `clock`: a fixture clock (domain `fixture`, wall time plus an offset) moved forward only on the control listener (`POST /_fixture/clock {"advance_ms": N}`); needs `--fixture-control` (CMP-60). The build descriptor names the clock's domain and offset.
- `tiny-tracker all --supervise`: the backend and the MCP server as two children, each restarted on the same port when it stops; a new state line after every restart; `boot_id`, `restart_count` and a `supervision` member in the build descriptor (CMP-61, CMP-62).
- Crash fault points `backend/before-commit/crash`, `backend/after-commit/crash` and `mcp/after-backend-reply/crash`, under `--supervise` only (CMP-63), with arming kept by the supervisor so that a `once` fault does not re-arm on a restart. `--fault POINT[:once]` arms at start.

### 0.3.0 integration (streams D and E on 0.2.0)
- Stream D on seams v2.1: the key states `completed`, `pending`, `fenced` and `expired` in the frozen keyed order; a pending key answers 409 `in_progress` whatever the body; an expired key with the same request answers 410 `key_expired` as a replay of its tombstone. A run reset fences that run's pending keys with a journal `fence` line; run allocations are journalled (`run-alloc`) and restored, so run ownership survives a restart; a settle-by-lookup fence is a `lookup-fence` line (additive). Execution records and operation records answer for commits made before a restart.
- The MCP layer answers 410 `key_expired` as outcome `applied`, `replayed: true`, repeat `read_first`, with the tombstone's execution id.
- CMP-50: `durable` needs `strict-input` (refused at start). Stream D's rule for backend features in `server` is CMP-54. `key-store-durable` and `settle-by-client-reference` turn a default-only `lookup` off, as `key-store-honest` does.
- Crash points are armed through the fault controller (`POST /_fixture/faults`) into the supervisor's arming store; a crash point in one process is refused 409 `needs_supervise`, and takes no selector but `once`. `--fault` arms at start (CMP-7); under `--supervise` only crash points (CMP-64). A backend crash firing reaches the ledger before the process stops.
- Under `--supervise` with `durable`, a restarted backend child takes over the dead child's data-dir lock (a killed child its supervisor has not reaped yet counts as gone). `/build` fills `durability` and `journal.head`; the schema types the `supervision` member.
- `--data-dir` goes through stream F's private-directory check (`src/private-dir.ts`).
- `verify/python/tt_recount.py --journal` reads the journal as tiny-tracker writes it (commit lines, checksums, a digest recomputed from each committed body), with `--principal`.
- `harness/a5_durable.sh` and `docs/a5-durable.md`: the durable A5 run with a restart mid-window, wall clock offset 0, control off.

### Changed in the default profile (ships with 0.3.0; `--profile 0.1` keeps the 0.1.0 behaviour)
- The default profile also turns on `inflight` and `retention` (owner decision 1, after the 0.3.0 gate). A same-key call while the first is being applied answers `in_progress` (outcome `unknown`, repeat with the same key); every key-accepting tool's description ends with the retention sentence ("A key is remembered for 7 days; …"); keys are kept 7 days with tombstones (`--key-expiry refuse`); `--defect all` includes `in-progress-reported-not-applied` and `settle-miss-reported-not-applied`. `durable` stays named: it needs `--data-dir`. The default build's `build_hash` changes with its feature set.
- `tiny-tracker server` is not refused for the default's `inflight` and `retention` (CMP-54 refuses them only when named). Its tools state the retention its backend states: at start it reads `retention_ms` from the backend's fence route (a peek, `{"fence": false}`, which writes nothing). A `--key-retention` (or `TRACKER_KEY_RETENTION`) that differs from the backend's is refused; where the backend states none (no `inflight` or `retention` there, or not reachable at start) the given value is stated, and with none given the tools say the retention is not known rather than name 7 days.
- With `retention`, every answer of the fence route (`POST /operations/:key/fence`) carries `retention_ms`, the configured retention (not one shortened by `key-expires-early`). Additive.
- `tiny-tracker server` refuses `--key-expiry` and `TRACKER_KEY_EXPIRY` (exit 2): the expiry policy is the backend's, and `server` would have ignored it. Give it where the backend runs.
- `key-store-durable` and `settle-by-client-reference` turn a default-only `inflight` off as well as `lookup` (CMP-53); the state line names both in `features_off`. `settle-by-lookup` runs with the default's `inflight`, without naming it.

## 0.2.0 (18 Nov 2026) for MWS 0.9

The first shared-fixture release: evidence, execution records, lookup, principals, the execution ledger and server-side faults. `--profile 0.1` keeps the surface of the published 0.1.0, checked call for call against a transcript captured from its tarball; the default profile's changes are listed below.

### Added
- `--profile 0.1`: exactly the surface of the published 0.1.0, kept in every later release. `--profile default` is what runs when none is named.
- `--features` (`TRACKER_FEATURES`): strict feature switches; a name not built in this version stops the process (exit 2) and says which release builds it. Built now: `strict-input` (the backend checks idempotency keys itself and refuses strings that are not well-formed Unicode) and `evidence` (a stub: the read-only evidence namespace with `GET /build`, the build descriptor and its two hashes, mirrored in the MCP instructions and every result's `_meta`; run and operation tags from request `_meta` stamped on every backend request).
- `--fixture-control`: a separate, hardened loopback control listener with its own token (run ids; clock and fault tables, read-only for now).
- Tokens for the evidence namespace and the control listener are read from the environment or a 0600 file, never from the command line, and never printed.
- A compatibility table: illegal combinations of profile, features, defects, variants, faults and process layout stop the process (exit 2).
- Defects carry a `requires` list; `--defect all` means every defect valid for the active features. The backend has its own defect registry (seams, banner, refusal rules), and a computed defect placement map.
- `--token-dir`: a 0700 folder where evidence and control tokens are generated (0600) when not supplied; only its path is printed.
- Each write's committed transaction carries its complete post-state (objects, deletes, id counters, owners, applied-write entries), its request body and reply headers, the boot id and one record-clock time used for every stored time. A re-sent If-Match write that was already applied is reported as a replay, not a second commit. A journal failure is reported to the ledger. Backend fault hooks (before and after the commit section) and a run reset through the commit path.
- Seams v2.1: key records answer in a fixed order (completed, pending as 409 `in_progress`, fenced as 409 `key_fenced`, expired as 410 `key_expired`), and every keyed answer reaches the ledger. A run reset fences its run's pending keys, so a write in flight during the reset never lands after it. Run ids are random; with the control listener on, a run tag that was never allocated is refused. A generated token file is written whole before it appears.
- Integration (0.2.0): a tagged write that waited before its commit section while its run was reset is refused 409 `run_reset` and applies nothing; any internal error answer is recorded in the ledger as a refusal (500 `internal`); the MCP layer reports 409 `in_progress` as outcome `unknown` (repeat with the same key), not as nothing written. Fenced keys never expire (owner decision). The evidence route `GET /executions/:id` takes `?principal=` optionally; `fx-check` is a second command of the package.
- The backend's single commit path (validate, journal, apply, ledger, reply), an injected clock for every timestamp, typed backend seams, principals with key records scoped by principal, and frozen record field names (`docs/INTERFACES.md`).
- RFC 8785 canonical bytes and domain-tagged SHA-256 digests, with cross-language vectors (`vectors/digest-1.json`) and a standard-library Python verifier (`verify/python`).
- `FIXTURE.md`, JSON Schemas with `$id`s (`schemas/`), and decision records (`docs/decisions/`).

### Stream C
- `harness/`: the lost-response contract adapter 0.2.0 (`harness/adapters/tiny_tracker.py`), pinned to the contract at `92bf1ba`. It counts effects from the execution ledger, drops the lost response server-side (`mcp/after-backend-reply/drop`), serves exactly one digest (`result_digest`), recomputes it with the domain tag, and recovers by key alone through `get_operation`. A3's key-only verdict is labelled self-attested until the driver compares recovered digests. `harness/adapter_config.py` prints a config for a running build; `harness/selfcheck.py` exercises the adapter, or runs the driver itself.
- `fx-check` (`src/fx-check.ts`): checks a running fixture's FX- properties through its evidence API and answers each one held, violated, not checked or not applicable. Read-only by default; `--probe` writes probe tickets in a run of its own and resets it.
- `expected/generate.mjs`: generates known-answer files keyed by `build_hash`, by running each build; `expected/builds-0.2.0.json` lists the 0.2.0 builds.
- `verify/python/tt_recount.py`: recounts executions and objects from the export, the ledger, the execution records and (from 0.3.0) the journal, independently of tiny-tracker.

### Changed in the default profile (ships with 0.2.0; `--profile 0.1` keeps the 0.1.0 behaviour except where noted)
- The default profile turns on `execution-records`, `lookup` and `principals` (owner decision 1). `tools/list` gains `get_operation` and `get_execution` (18 tools), every committed write's answer carries `Tiny-Tracker-Execution`, and `--defect all` includes `lookup-reexecutes`; every other text and structured result is the 0.1.0 one. `TRACKER_VARIANTS=key-store-honest` turns `lookup` off for that build (lookup cannot see the keys the variant keeps; owner decision, 16 Nov 2026): the state line carries `features_off`, a notice goes to stderr, and the build descriptor and `build_hash` follow the features the build runs. A `lookup` named with `--features` or `TRACKER_FEATURES` alongside the variant is refused (CMP-5, exit 2). Under `--profile 0.1` the variant runs as in 0.1.0.
- `tiny-tracker server --backend-defect NAME` stops with exit 2 instead of starting with the backend defect silently unused (CMP-9).
- The `evidence` feature runs with `tiny-tracker all` only (CMP-11).
- A start whose command line holds one of its tokens (8 characters or more), or where two tokens are equal, stops with exit 2. This holds under every profile, `--profile 0.1` included.

### Fixed
- A re-sent If-Match write from another principal was answered as a replay of the first principal's write; it now gets the normal 412.
- A failure completing a key record after the journal append no longer skips the ledger: the ledger is told, then the store stops.
- The 0.1.0 entry below says "41 deliberate defects"; 0.1.0 shipped 47 MCP-layer defects and 1 backend defect.
- `fx-check`: FX-LOOK-2's never-written key no longer shares its first eight characters with the probe keys, so `lookup-wrong-record` cannot mask `lookup-reexecutes`.

### Stream A
- Feature `execution-records`: one execution record per applied write (`X-<seq>`), with the principal, the run and operation tags, the request's `fingerprint_hash` and the committed result's RFC 8785 bytes and digest. Each committed answer, and each replay, carries `Tiny-Tracker-Execution`; `GET /executions/:id` with the caller's token shows that principal's records.
- Feature `lookup`: `GET /operations/:key` in the caller's own scope; a miss answers "no record of this key now", which never means nothing was written. New read-only tools `get_operation` and `get_execution`, listed only with the feature.
- Feature `principals`: `TRACKER_BACKEND_TOKENS_FILE` (0600 JSON) gives two or more principals. Every token must differ and none may be on the command line; records and lookups are scoped to the principal.
- The evidence read side (`EvidenceReader`) with the `?principal=<id>` rule, and `TRACKER_EVIDENCE_LISTEN` (container mode): the evidence routes alone, on another address, behind the evidence token.
- Six fixture defects, each needing its features: `digest-of-current-state`, `replay-digest-mismatch`, `digest-not-canonical`, `lookup-wrong-record`, `lookup-unscoped` (backend) and `lookup-reexecutes` (MCP layer, MWS-ANN-1).
- Compatibility rules CMP-20 (`lookup` needs `execution-records`) and CMP-21 (`principals` runs where the backend runs).

### Stream B
- `ledger` feature: an append-only execution ledger, one of the store's commit sinks, written below every MCP-layer defect. It records every write, replay and refusal with its principal, run and operation tags and request fingerprint, a write whose journal append failed (`journal-unavailable`), a run reset (from the reset's own commit), and the fixture's own start, fault arming and firing and run allocation. A ledger that cannot append stops the store (503). Read at `GET /ledger` (filters, paging, JSONL) and in `GET /export` with the evidence token, for one principal (`?principal=`, required when more than one is configured). Needs `evidence` and `strict-input`.
- `faults` feature: faults armed on the control listener (`POST /_fixture/faults`), never on the command line. Backend points fire through the backend fault hooks and MCP points through the MCP result hook. This version arms `mcp/after-backend-reply/drop`, which holds the MCP answer after the backend committed (the lost response, server-side), selected by tool, run, operation, nth and count; when the hold ends the true answer is sent. Every arming and firing is a ledger entry. Needs the ledger and `--fixture-control`.
- CMP-7 now refuses a fault armed at start only without the faults feature or for a point this build cannot arm (it used to refuse every fault).
- The build descriptor's `fixture_api` is `fixture-api/1`: the control API arms faults and resets runs.
- `POST /_fixture/runs/:id/reset` removes one principal's run's objects and key records as one commit through the commit path, recorded in the ledger from that commit; run allocation is recorded too, and runs are allocated only for configured principals.
- `GET /executions`, `GET /executions/:id` and `GET /operations/:key` serve execution and operation records in the evidence namespace when their features are on; otherwise they answer 501 and name the feature.
- Caps: 100000 ledger entries per process, 32 armed faults, 16 held answers, a 10-minute hold, 32 control connections and a 10-second request timeout on the control listener.

## 0.1.0 (16 Nov 2026) for MWS 0.9

First published version. Follows the MCP Write-Safety Requirements 0.9 (37 requirements).

### Changed
- The conflict text and `get_ticket`'s text give state values unambiguously (proposal P-8 of the conflict-wording study, re-pilot 3; spec R12-1): label names are quoted as a JSON list (`labels ["content", "v3"]`), and the version is given on its own (`current expected_version: 3`; in `get_ticket`, on its own line, with each label's id beside its quoted name in JSON); an assignee is quoted too (`assignee "ann"`; `assignee none` only when there is none); `list_tickets` quotes each title as a JSON string and gives the version on its own (`T-3 [docs] open "Fix the docs"; current expected_version: 3`). The texts changed, so the build hash moves: a study run must name the build it used.

### Added (spec R15-3)
- Defect `shape-text-says-all-saved` (MWS-ATOM-1): `bulk_update_tickets` writes one by one, and after a partial apply its shape is right (`"outcome": "partial"`, each ticket in `items` with its own outcome) but its sentence says "All 3 tickets saved". A tester reads the sentence by the declaration's pattern for a statement that the whole write took effect (`patterns.applied_all`). The self-test's MWS-ATOM-1 check reads that sentence too.

### Added
- A small issue tracker (backend and MCP server, Streamable HTTP, protocol revisions 2026-07-28 and 2025-11-25) whose correct build is meant to meet every applicable requirement.
- 41 deliberate defects, one per requirement (four for MWS-RETRY-2), each in its own file and off unless named with `--defect`.
- MWS-RETRY-2 (spec R8-3): `create_project` accepts an `idempotency_key`, sent to the backend (a new key for a key that exists is refused by the duplicate check, a refusal on its own merits). Two defects: `retry-without-key` (after a broken connection, `create_ticket` re-sends the create without its key, so it is applied twice) and `key-store-in-memory` (keys kept only in the server's memory, so a repeat after a restart applies the create again). A correct variant, `key-store-honest` (`TRACKER_VARIANTS`, with `TRACKER_KEY_JOURNAL`): keys kept by the server with a journal of used keys, so that after a restart a repeat is refused, never applied twice. The self-test's MWS-RETRY-2 check cuts one backend answer and restarts the server.
- A self-test that checks each defect trips its own requirement and, with every defect on, that no defect hides another.
- Settings for the launch requirements: read-only mode (`TRACKER_READ_ONLY`), an allow-list (`TRACKER_TOOLS`) and a deny-list (`TRACKER_DENY_TOOLS`), each refusing to start on a value it does not recognise.
- Tickets carry a free-text `description` (may be empty) and a nested `details` object (`component`, `severity`) whose sub-fields an update sets one by one, so the empty-string and nested probes of MWS-UPD-1 can be shown.
- `update_ticket`, `set_labels` and `delete_ticket` need `expected_version`, or `force: true` (default off) to write without the check.
