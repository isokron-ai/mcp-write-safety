# Changelog

All notable changes to `@mcp-write-safety/writecheck` (the `mcp-writecheck` command). The format follows Keep a Changelog; versions follow Semantic Versioning once published.

## Unreleased

### Added
- MWS-IN-5 is a scoped, automated search (scenario `in5-search`). The server owner no longer needs to declare `try_values` for the requirement to be searched: for each argument of each tool the search starts from (a resource's read call and declared list calls, its create tool, and its update tool on scratch objects of the tester's own), after a base call that succeeded, it sends values valid by the input schema that commonly meet an undeclared limit (string lengths 0 to 65536 within the declared bounds, character classes beside a plain value of the same UTF-16 length, format extremes, number extremes on write tools and up to a declared maximum on read tools, arrays of up to 1000 items on read tools and of 0, 1, 2 and a declared maxItems on write tools) and the bounds a description or a document listed under the new `in5.docs` states in words, interleaved over the arguments in a fixed scrambled order. A refusal is counted as a fixed single-argument constraint by the declaration (`fixed_constraints`, as before), or by the tester's differential reading: two neighbouring values accepted in the same context (one of them not empty, for an upper bound), the refusal repeated in a fresh context with another argument varied and its neighbour accepted again after it, and on an order a monotonic boundary found by bisection, which the record gives (for example `maxLength 100`). Until MWS 0.10 accepts that reading, a constraint it alone confirms is recorded in a `not observed` record as a candidate, seen, not judged, with the boundary; `--in5-reading=tester` (on `run`, `rerun`, `recheck`) records it as `violated` where the fresh context refused it twice (neighbour, refusal, neighbour, refusal, with the same refusal text as the search) and the refusal names the argument and the kind of rule. On every tool numbers are 0, ±1 and declared bounds only; on write tools arguments named like costly quantities are not probed unless `in5.allow_args` names them. Refusals that name a rate limit, a request-size limit (413), the backend's state or the caller's permissions, and unknown outcomes, are left out. The record is `violated` or `not observed`, or `not tested` where no call was judged, with the scope in `numbers` (`args_total`, `args_searchable`, `args_judged`, `args_complete`, `args_skipped`, `probes`, `judged`, `refusals`, `confirmed`, `candidates`). New limits `in5_probes` (calls per tool, default 80), `in5_creates` (calls to a create tool, default 10) and `in5_payload_bytes` (default 65536); undeclared, they are not written into the plan's limits. The plan counts the search's calls, writes and creates, so every plan hash changes; the search stops short of the writes the later checks plan. Write tools the search does not start from get an MWS-IN-5 record `not tested` with the reason. The declared `try_values` are sent by the search on its scratch objects; where the search does not search the update tool (a fixture-only resource, or cleanup `leave`), schema-probes sends them on the object under test as before. schema-probes gives the MWS-IN-5 record of an update tool it halted (spec R15-4). On tiny-tracker the search finds `--defect undeclared-title-limit` (`maxLength 100`) with no declaration, and the correct build gives `not observed`.
- Cells (docs/CELLS.md): every MUST requirement on every declared write tool, and each server-level MUST requirement (MWS-CFG-1..3) on the server, now has at least one record. Where no check made one, the run adds `not applicable` with the written applicability rule that excludes the cell (rule ids such as `TGT-3.server-id`), or `not tested`. Records are merged per tool across resources and scenarios into `cells`, a new top-level array of `results.json` (key, verdict, applicability, rule, resources, record indexes); each record of a cell carries `cell: "<requirement>@<tool>"`. Read tools are not cells. `report.md` has a Cells table. `recheck` rebuilds the cells.
- Evidence validity (docs/CELLS.md): every `violated` record carries `validity` (`valid`, `platform` for attribution unresolved, or `harness-suspect`, with the rules V-STEPS, V-RUN, V-ACK, V-READBACK it did not meet, and whether the fault was injected). Only a run cut short by the write budget, a rate limit or an interrupt fails V-RUN. Catalog, launch and ledger evidence is exempt from V-STEPS and names its basis. A check can state its evidence through the new `evidence` option of `result()`. The held-request MWS-CONC-1 violation now carries its trace steps.
- Pair budget (opt-in): `limits.pair_budget` or `--pair-budget RxP` (plan, run, rerun, demo), and `limits.pair_repeats`. With a budget, the barrier-pair test runs it, and the MWS-CONC-3 pairs record states the budget, the pairs run per repeat and whether the budget was met; an undeclared `write_budget` is sized to fit. Without one, defaults, records and plan hashes are as before. The plan prints the estimated time for its writes at `writes_per_second`.
- A tool the declaration gives a write role keeps its cells even when it declares `readOnlyHint: true`. CONC-2, CONC-4 and TGT-1 apply where the schema has a version-like or container-like argument. A violation whose evidence does not count ranks below `held` in its cell (`V?` in the report). `cells` is optional in the schema.
- Read extraction (`decode.extract`): for a server that answers its JSON inside markup or prose (the whole answer wrapped in `<insecure-content>…</insecure-content>`, say), a read, list, guard or `server.decode.<tool>` may declare `decode: { extract: { between: [start, end] } }` or `{ extract: { regex: "<pattern with one capture group>" } }`; the JSON is taken out of the answer's text and parsed before any path reads it. `between` tries each end marker after the start until the text parses; a regex runs under a 100 ms limit per answer, and at most 256 KiB of text is searched. Only an answer without structuredContent and without an error is extracted, and neither the structured refusal signals nor a declared `outcome_field` read the extracted document, unless `refusals: true` is declared; the patterns read the text as received; an adopted result shape is not read from it. Where nothing is found the answer has no data and its record carries `extract_failed`. An invalid regex, one without exactly one capture group, one whose group is not delimited on both sides (optional delimiters included), or one with a quantified group holding a quantifier is refused at load (so `plan` refuses it). Each extracted call record in `results.json` carries `extracted: { from: "text", by, basis: "manifest", refusals }`, and `target.mcp.notes` says once per tool that extraction was used or failed. No Python-repr parsing. The `decode` member keeps its `json` / `none` forms; the object form is `{ mode, extract }`.
- Per-session init (`session.init`): a list of `{ tool, args, read_only }` calls made on every MCP session the run opens (each server process, each HTTP session, clean-up and launch checks included), once, before the session's first other tools/call, and, from the confirmed plan on, at the end of every new connection's handshake (so no init call falls inside a barrier). For a server that connects to its backend only when a call carries the connection settings (`connect(host, user, password)`). `args` may use only `{{env.NAME}}`, and a value under a secret-like name must be one; every such value is a secret from three characters (redacted in the capture, history, ledger and reports). tools/list does not trigger it before the plan is confirmed, so `plan` still makes no tool call. A call counts against the write budget unless the operator declares `read_only: true` (a server's `readOnlyHint` does not exempt it); the plan lists each init call (templates as written) and whether it is counted, and warns that counted ones are not in the "at most" figure. The clean-up's init is counted but never refused. A failed init call stops the run with `stopped: session.init[i] (<tool>) failed on session <label>, before any probe on it: <reason>`; on a server a check starts for itself it makes that check `not tested`; on the clean-up it is a clean-up failure, retried once. Where the tenant guard fails with a "not connected" answer, the refusal points to `session.init`.
- Plan hash: only manifests that use the new members get a new hash (their bytes change, and a `session_init` member is added to the plan only where `session.init` is declared); every other manifest keeps its plan hash.

### Fixed
- A record written twice word for word (t11: the MWS-IN records of a tool that is both the read and the update tool) is kept once.
- MWS-CONC-2 on an update tool with no version argument that is also listed in `no_version_check` gets one record, `not applicable`, instead of that and a contradicting `not tested` (t23).
- A cell is no longer split by resource: delete_ticket, held under one resource and not tested under another (tiny-tracker `ticket-replace`), is one held cell.
- `session.init` on a server a check starts for itself: a failed init no longer voids the whole check. Only the launch setting it was started for (an MWS-CFG-1 value, the CFG-2 deny-list, the CFG-4 allow-list, the CFG-3 read-only start) or the MWS-RETRY-2 restart step it belongs to is `not tested`, with the reason; observations already gathered keep their verdicts.
- `session.init` secret-like names are matched on whole name parts, case ignored, camelCase and compounds included (`accessToken`, `passwd2`, `dbPassword`, `authToken`, `clientSecret`, `privateKey`, `Authorization`); a descriptor last part (`token_type`, `auth_mode`, `secretName`, `password_policy`), a limit (`max_tokens`) and a part that only contains a marker (`bypass`, `passport`, `tokenizer`, `primary_key`) are not secret-like; `key` counts alone or with api/private/access/secret/client/signing/encryption/master. A number is refused only under a password-type name. Lists are checked (strings under a secret-like name, the element after a secret-like flag or `-p`, `--token=<literal>`, `PASSWORD=<literal>`), and so are `{ name, value }` header pairs; a literal URL is refused only if it carries user-info or a secret-like query parameter.
- The short-value redaction floor (three characters) applies only to init values given under a secret-like name; every other init value is masked from six characters, like every other secret.
- MWS-CFG-3 (read-only mode) now also calls each tool marked read-only (`readOnlyHint: true`, or a declared read tool) that has an entry in the manifest's `calls` whose arguments name an object of the run, with that entry's arguments and resource as the annotation checks use them, and reads the object back. Before, such a tool was left out (or, with `{{id}}` in its arguments, called and counted as a write tool), so a read-only mode decided by annotations could let a read-only-marked tool write and still be `held`. A change through it is now `violated`, and the record names the tool and says it is marked read-only; a refusal, or a final answer with no change to the watched object, counts toward `held`, so its successful answer no longer leaves MWS-CFG-3 `not tested`; a call that could not be made or failed without a refusal (a timeout, a lost connection, an error MCP defines for the case), an `input_required` or task answer, or an object that could not be read back, leaves it `not tested`, and the record names the tool and why. A `calls` tool (marked read-only or a declared write tool) that deletes its object in read-only mode is now `violated`; before, a declared one that deleted and answered with an error was read as refused and gave a false `held`. The deny-list trial of MWS-CFG-2 calls the same tools and judges them the same way; MWS-CFG-1 compares the declared write tools only. A tool marked read-only with no `calls` entry is still not called. The plan's MWS-CFG-3 line (and the MWS-CFG-2 deny-list line) names these tools, so the plan hash changes only for manifests with `settings.read_only` or a deny-list in `settings.tool_filters` and a `calls` entry, naming an object of the run, for a tool marked read-only.
- Wrapped results are read (t17): a tool that answers structuredContent `{"result": "<a JSON document as a string>"}`, as Python FastMCP does with a wrap-result output schema, had its answer read from the wrapper, so paths found nothing (a read's `items`/`match`, the fixture lookup, `target.guard.path`) and the fixture was "not found". The JSON inside the string now replaces structuredContent in every reading of that tool's structured answer, for reads and writes: paths, the declared `outcome_field`, the structured signals (conflict, version-required, validation), the CONC-2/4/6 conflict readings, the text the patterns search, and an adopted result shape (read from the decoded document, as the patterns are). It applies only where the tool's `outputSchema` marks a wrapped result (`result` as its only property, of type string or untyped, with or without `x-fastmcp-wrap-result`) or the manifest declares `decode: json`, and only where structuredContent has `result` as its only member and that string is a JSON object or array. `decode: none` (on `read`, `list`, `target.guard`, or per tool under the new `server.decode`) keeps a marked tool's results as received. Each decoded call record carries `decoded` and `raw_structured` (structuredContent as received), and `target.mcp.notes` names each decoded tool and why. Results of servers that do not wrap are read as before; plan hashes of existing manifests do not change.
- A backend URL in the server's command line (`server.stdio`, `server.launch.command`; e.g. `redis://host:6379` or `--url=postgres://…`) is now a target host. It is shown in the plan and checked by the production-host refusal; before, such a host was neither. Plans for servers with such an argument get a new hash. A run left open by an earlier version on such a manifest is refused at cleanup ("environment now points at …") and needs `--abandon`.
- A backend host given without a URL is now a target host too: host variables (`DB_HOST` with `DB_PORT`, `HOST`, `PGHOST`, `*_SERVERS`, `*_ADDR`, `*_BROKERS`, …; comma lists and `host,1433` read), host flags (`--host`, `--db-host`, `--server`, `-h`, `-H`) with their port flag, and `-e`/`--env NAME=value` in the server's command line. Where in doubt a host is read; a listen address (BIND/LISTEN names, and a launched server's one-word `HOST` or unprefixed `--host`) and a single word under a SERVER/ADDR/ENDPOINT name are read only when they look like production. `sh -c` strings are not parsed. The rules are in MANIFEST.md under target. Such a host is shown in the plan and checked by the production-host refusal; before, the plan said "none". Plans for servers with such a variable or flag get a new hash. A run left open by an earlier version on such a manifest is refused at cleanup ("environment now points at …") and needs `--abandon`.

### Changed: before/after hardening (test hash scheme `mws-test-hash/2`)
- New test-hash scheme `mws-test-hash/2` (`identity.test_hash`). Every record carries `test_inputs`: the tester build (commit and dirty flag), a hash of every input other than the tools (`rest`) and of its context, a shape per tool of the arguments the test sends (per-argument constraint hashes, nested properties, array items, required names), for MWS-IN-1 to IN-7 a shape of every probed argument, the judged annotations or description, and for MWS-IN-5 the reading and the sha256 of each `in5.docs` document. `test_hash` is computed from them. Files under `mws-test-hash/1` stay readable; compare never joins records hashed under different schemes and says so (`scheme-changed`).
- The launch checks (MWS-CFG-*), which call the tools of every resource in the read-only and deny modes, hash every resource block and the shapes of every tool those blocks and `calls` name; a tool the manifest's `calls` declares hashes the arguments its `args` send (annotation effects). Dropping a resource or retyping an argument such a call sends is another test.
- compare: a cell whose self-attested answer changed is `changed`, never `unchanged`; for not tested against not applicable the run's own cell decides, as the header said.
- Review of the hardening (19 November 2026): the read-after-write further probes, the list-edit address arguments and `selector.narrow` enter the test hash (`test_inputs.chosen`, tool shapes); rule A counts a relaxation as another test where the check acts on `required` (MWS-IN-1, MWS-CONC-2), and also a required argument the test does not send that is no longer required (an argument newly declared under `additionalProperties: false` stays rule A, as decided, and is said under the cell); an unstamped or dirty tester build claims no regression; a record whose stored hash does not follow from its test inputs is `hash-mismatch`; `recheck --sign-key` needs an original signed by the key given with `--pubkey` (or `--allow-unsigned`, recorded in `rechecked_by.original_signature`), and compare warns on a recheck of an unpinned original. No procedure version changed; the scheme stays `mws-test-hash/2` (unpublished).
- New hash inputs: `server.restart`, `server.processes`, `server.decode` (and its `extract`) and `server.protocol`; `writes_per_second` for MWS-RETRY-2; the review answers in force (a `--review` file); for MWS-IN-5 the tool description, argument descriptions and the `in5.docs` contents. Annotation keywords (`description`, `title`, `examples`, `$comment`, `deprecated`) no longer enter any other requirement's hash. A top-level `$ref`, `$anchor` references and draft-07 `dependencies` are followed; a `$ref` pointer with a bare `%` and an argument named `constructor` no longer crash the narrowing.
- compare applies owner rule A (decided 18 November 2026): two records whose hashes differ are the same test when the same call is accepted by both builds: an added optional argument (also one the manifest already sends), an added optional nested property, or a required argument relaxed to optional (`RELAXED_REQUIRED_IS_SAME_TEST`). Every tolerated difference is listed per cell (`same_test_because`); a tightening is a changed test.
- Records join per slot and case: the creates check gives each record a `case` (`create:<name>`, `update`, `failure:<name>`, `delete`). Several records in one slot without case ids never give a fix where their counts differ or an after record is not tested, not observed or `violated?`; a case that goes held → violated beside a still-violated sibling is a slot regression (exit 1).
- Schema probes: a probed argument that is gone is a changed test (never fixed); an added optional argument no longer makes MWS-IN-2/3/6/7 subject-changed; held → violated across a change of the judged schema is regressed.
- Set-up rule: a set-up record (a resource whose set-up failed) is joined as held where the other build set the same resource up with the same writes and passed.
- compare refuses a file whose results signature does not verify (exit 3), with or without `--pubkey`; unsigned or unpinned input needs `--allow-unsigned` (exit 2 otherwise) and is labelled in compare.json and compare.md.
- A fix is claimed only between records judged by one stated, clean tester build (`tester-unpinned` otherwise); `same.tester` is false for two files that state no tester build or a dirty one; `judged_by` lists the builds that judged a file's records.
- compare warns on swapped files (start times), the same file or run on both sides, two runs of one server commit, and violations newly found in cells the before build did not test (`newly_found`; `--fail-on-new-violation true` exits 1).

### Fixed: recheck
- `recheck` by the build that made a run keeps every verdict: the whole-run adjustments (a declared explicit override for MWS-CONC-1, an apply with field ownership for MWS-CONC-2, the first write after a create for MWS-UPD-1) are one step shared with `run`. The first-write finding is kept on the resource's observations (`first_write`) and read back from older files' records.
- `recheck` refuses a folder whose `results.json` carries a results signature that does not verify (exit 3), before anything is written or signed again.
- `recheck` hashes a re-evaluated record from its recorded test inputs (naming the rechecking build) instead of the run folder's redacted copies, and applies the run's `--pair-budget` (`identity.hash_inputs`).
- The run folder's manifest copy stays YAML where a header-like key names a variable in a flow mapping; the catalog copy keeps the schema of an argument named like a credential (`password`), masking such a key only where its value is a string.

### Added: run identity, signed results, compare
- `results.identity` (`mws-identity/1`): the tester build and git commit (stamped by `npm run build`), the MWS version, the manifest sha256, the plan hash, a tool-list fingerprint, the server build (repo, commit, tag, image, recipe; launch command and transport) and backend images, the runner (OS, architecture, Node.js, GitHub Actions run), start and finish, and `gaps`: every member not stated or not pinned (including a dirty, unknown or stale tester stamp). The build comes from the new optional `target.provenance`, a `--provenance` file, or `--server-repo`, `--server-commit`, `--server-tag`, `--server-image` and `--backend-image name=ref` on `run` and `rerun`; an abbreviated commit or an unknown key is refused before the run writes anything. A manifest with `target.provenance` gets a new manifest sha256 and plan hash; others do not.
- `test_hash` on every record (`mws-test-hash/1`): sha256 over exactly what defines that record's test. Tools enter as narrowed input schemas (the arguments the test uses, `required` restricted to them, the names of other required arguments), so a fix that only adds optional arguments keeps the hash; descriptions, annotations and output schemas enter only for the requirements that judge them (schema for MWS-IN-2/3/5/6/7, annotations for MWS-ANN-*, description for MWS-CONC-5, RETRY-2, TGT-3), whose records also carry `test_hash_core`. `target.guard`, the rate for MWS-CONC-* records and the MWS-IN-5 reading (where the build has it) are included. MANIFEST.md, Run identity, lists the inputs.
- `--sign-key FILE` (or `MWSC_SIGN_KEY`): an Ed25519 signature of results.json in `evidence.signature` (`mws-results-signature/1`: RFC 8785 canonical JSON with the signature replaced by its bound members, a domain line, the kronicle-lite key id). Key material is never printed; an embedded public key is never read as a path. `evidence.signature` stays a string for the ssh signature of `SHA256SUMS` alone. `mcp-writecheck verify-results <file> --pubkey KEY` checks it against a pinned key, and refuses a file that repeats a member name; an unreadable key exits 2. Unsigned results are allowed and flagged. `recheck` leaves its copy unsigned (or signs it with `--sign-key`), hashes the records it re-evaluated, and sets `identity.rechecked_by`.
- `mcp-writecheck compare <before> <after>`: per cell, verdicts rolled up by MWS 8.2 rule 13 (violated, platform, held, not observed, not tested), joined slot by slot on equal test hashes; `fixed` only where every slot violated before is held after; a slot tested on one build only is a coverage change; `schema-fixed` where a requirement that judges the schema saw the schema change and the violation go; slot regressions inside a cell are listed and fail the command unless `--fail-on-slot-regression false`. Writes `compare.json` (`schema/mws-compare-1.schema.json`) and `compare.md`; refuses different MWS versions; exit 1 on a regression.
- report.md's Evidence section states the run identity, its gaps and how to verify the results signature.
- Compatibility: the new members are optional additions to `mws-results/1`, which keeps its name; a validator using an earlier release's schema rejects `identity` (MANIFEST.md, Run identity, Compatibility).

## 0.1.0 (16 Nov 2026): preview for MWS 0.9

First published version. Follows the MCP Write-Safety Requirements 0.9 (37 requirements, 26 MUST, 11 SHOULD).

### Added
- `run`, `plan`, `review`, `recheck`, `rerun`, `cleanup`, `init` and `demo` commands; `catalog` (catalog-only mode: the verdicts that need only `tools/list`, no tool call, no account).
- Executable checks for a stated subset of the 37 requirements; the README's coverage table lists each requirement as covered in full or in part, and what is not built is reported `not tested` with the reason.
- The backend gate (base-URL rewrite or `node --import` hook) for proxy-assisted tests: held requests, failed requests, and answers cut after the backend applied the write.
- Results per write path in `results.json` (schema `mws-results-1`), `report.md` (violations first), `junit.xml`, a redacted capture of every call, `SHA256SUMS` and an optional ssh signature.
- Seat belts: target confirmation, plan hash, tenant guard, write budget, run prefix on every object, a ledger and cleanup, egress limited to the declared hosts.
