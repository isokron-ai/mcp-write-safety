# Decisions

This file records decisions about the MCP Write-Safety Requirements (MWS): what was decided, when, and what the alternatives were. Rejections are recorded with their reasons. New entries are added at the end; entries are not rewritten.

## Founding decisions, 14 November 2026

A design for the standard, its test suite and its sample server was written and then compared with three independent design answers to the same brief. The comparison produced 22 questions, each with a recommended answer and alternatives. The owner (Joshua Bryan, IsoKron) approved the recommended answer to every one on 14 November 2026.

| # | Question | Decision (approved 14 November 2026) | Alternatives considered |
|---|---|---|---|
| 1 | Names and ID prefix | The standard is "MCP Write-Safety Requirements". Requirement IDs are prefixed `MWS-` (for example `MWS-UPD-1`, `MWS-CONC-1`). The test CLI is `mcp-writecheck`. The sample server is `tiny-tracker`. | The prefix `WS-` (reads as WebSocket and as the older WS-* web-service standards); three other names, one of whose abbreviations collides with the secure WebSocket scheme. |
| 2 | Rule set | 29 requirements in ten areas (UPD 2, CONC 4, TGT 3, RES 4, ATOM 2, RETRY 2, IN 4, CFG 3, ANN 4, SEC 1), 23 at MUST and 6 at SHOULD. Batch reads and catalog size are measured in an informative annex with no verdict. Six small changes are included: results are stated per write path; MWS-UPD-1 applies to field-patch tools and full-replace tools are judged by MWS-CONC-2 and MWS-CONC-3; MWS-RETRY-2 has two negative clauses; MWS-SEC-1 scans error results as well as successes; every requirement has a fixed "Known limitations" heading; an informative annex of mitigation patterns. | Ten rules; ten rules with sub-clauses; catalog size as a MUST with a token budget; a MUST to compensate for a backend that loses updates. Rejected because wrong-target and false-success findings appear in four of the five published audits and had no rule among the ten, because any size threshold is arbitrary, and because two published cases are platform behavior. |
| 3 | Levels or profiles | None. MUST and SHOULD with an applicability condition per requirement. | Two profiles (L1, L2). Rejected: a profile is a claim that can be printed. |
| 5 | Release shape | A public 0.9 draft, a 30-day comment window, then 1.0. | Straight to 1.0; publishing the text and sample server first and the CLI later. |
| 6 | Items first listed for later versions | Built during the comment window and shipped in 1.0 if they pass the same gates: cooperative hooks for in-process backends; a proxy mode with a generated certificate authority; drafting a declaration from a recorded session; a requirement for writes made before an `input_required` result; SARIF output; a database wire-level hold; an exploratory mode with generated sequences. | Hold them for 1.1 and 1.2; build only the cooperative hooks now. |
| 8 | Implementation language of the suite | Node 22 and TypeScript, two runtime dependencies. | A static binary in a compiled language. Rejected: it discards working code. |
| 9 | Forced-interleaving scope in 1.0 | Interposition by rewriting the server's backend base URL, and by a Node import hook. | Marking the proxy experimental; a proxy with a generated certificate authority as the main route; no proxy until later. Rejected: one published finding has its read-modify-write inside a single call, which a stale write cannot stage. |
| 10 | Verdict words | Seven: `violated`, `platform`, `held`, `not observed`, `not tested`, `not applicable`, `self-attested`. There is no "pass". | Pass/fail sets of four or six words. Rejected: none had a word for platform behavior, and "pass" is what gets quoted. |
| 11 | Dry run and confirmation | The planning step makes no tool calls. A run needs the target typed back and the hash of the plan. There is no `--yes`. | A dry run that sends wrong-type probes. Rejected: a published finding is a wrong-type value that was coerced and accepted, so such a probe is a write on a server with that defect. A `--yes` flag for CI. |
| 12 | Outside maintainers | Wait for inbound interest. State the path to a neutral home in 0.9. | Invite three to five maintainers now. |
| 13 | Cleanup when a server has no delete tool | An explicit cleanup policy is required per resource. With none, tests that create objects are `not tested`. | Minimal creates and a table of leftovers, with no policy required. |
| 14 | Licences | CC BY 4.0 for the text, Apache-2.0 for code, DCO sign-off for contributions. | MIT for the tools. |
| 15 | Signing of results | The user's own SSH key, an optional timestamp, and GitHub artifact attestations. The steward does not countersign results. | Keyless signing through a transparency log; a signature over canonical JSON. |
| 16 | Registry or archive of results | Never. | An opt-in public archive; a registry of signed result packs. Rejected: either becomes a leaderboard. |
| 18 | Email capture | None in the tool and none on the standard's site. | Capture in the tool. |
| 19 | Name-use policy | A short policy (section 15.5 of the specification). No trademark filing for now. | File a trademark. |
| 20 | Reading of `destructiveHint: false` | Published as "additive only", following the schema text. MWS follows the MCP specification if it clarifies otherwise. | A reading based on whether the tool checks a precondition. |
| 21 | Published identity | The author named on the standard is Joshua Bryan, IsoKron. Packages are published from an organization, not a personal account. | None. |
| 22 | Review gates | Three stops: after the 0.9 text (the owner reads all 29 normative sentences, collected in `NORMATIVE-SENTENCES.md`); after validation against the known servers; before any public push. | None. |

Entries 4, 7 and 17 concerned the steward's internal operations and are kept in the steward's own log.

Also approved with the above: rules that judge batch reads and catalog size are a verdict-free informative annex (Annex A); a normative non-findings chapter (section 10); a stated path to a neutral home (section 15.6).

## Drafting notes for 0.9, 14 November 2026

These are choices made while writing the 0.9 text. They are not owner decisions and are open for the owner's review.

| # | Choice | Reason |
|---|---|---|
| D1 | Each requirement is one normative sentence. The design's requirement texts ran to two or three sentences. | So that each can be read and judged on its own. |
| D2 | Three secondary SHOULD clauses in the design became informative guidance: a best-effort stale-write comparison where the backend has no version check (MWS-CONC-2, now Annex B-3); a conflict that carries the current version (MWS-CONC-4); a schema that advertises the backend's constraints (MWS-IN-3). The MUST to disclose undetected stale writes stays in MWS-CONC-2. | A consequence of D1 with the count fixed at 29. The alternative is to make them requirements of their own in a later version. |
| D3 | Three test methods are named: black-box, proxy-assisted and review-only. The design had five; its "control" became the control arm, which can be added to either automated method, and its "launch" became "black-box (launch)". | Fewer labels; attribution is a property of a result, not a separate method. |
| D4 | MWS-UPD-2 is stated as behavior (the edit lands on the element identified, or is refused) and not as a design rule (address by a stable identifier). | The behavior can be tested from outside. Stable identifiers are the guidance. |
| D5 | MWS-TGT-1 is limited to scope arguments. The design's first sentence ("a write affects exactly the objects its arguments identify") is a claim about all state, which a tester cannot force. | Consistency with the verdict rules. |
| D6 | MWS-RETRY-2 covers idempotency keys only. A repeat that carries a version is judged by MWS-CONC-2. | A repeated write with a consumed version is a conflict, not a replay. |
| D7 | The "does not expose runtime internals" clause of MWS-IN-4 became guidance. | It can be checked only by pattern matching. |
| D8 | MWS-ANN-1, MWS-ANN-2, MWS-ANN-3 and MWS-SEC-1 can produce only `violated` or `not observed`. | Each is a claim about all of a server's state or results. |
| D9 | For a requirement that admits `platform`, a reproduction without a control arm is `violated` with a required note that no control arm ran. | Follows the design's definition of `violated`. Listed as an open question for the owner. |
| D10 | The area IN applies to every tool, not only to write tools. | One of the cited findings concerns list tools, and input handling is shared. |
| D11 | An update tool's mode (field-patch or full-replace) is taken from its input schema, whatever its description says, and recorded in the tester's declaration. | In one cited finding the description said "replaces the whole rule" while the schema marked the fields optional; two testers would otherwise disagree about whether MWS-UPD-1 applies. |
| D12 | MWS-RES-1 is reduced to one clause: success only when the state the caller asked for is in effect. The design's second sentence ("a call that changed nothing says so or is an error") became guidance. | The second sentence also caught a call whose requested state was already in effect, such as the delete of an absent object, which one cited project treats as intended. |
| D13 | MWS-RES-2 says a failed write "MUST NOT be reported as a success" where the design said it "is a tool execution error with `isError: true`". A failure returned as a JSON-RPC error is therefore not a violation. | The published findings are failures reported as successes. The MCP schema says tool errors SHOULD be reported in the result, which is weaker than a MUST. |
| D14 | MWS-CONC-4 gained "MUST leave the object unchanged". "Whether a re-read is needed" moved from the requirement to guidance. | The first can be measured; the second can only be read. |
| D15 | MWS-CONC-2 no longer says separately that whole-object and delete tools "accept the version the caller read"; it is implied by the duty to refuse a stale write and is stated in the guidance. | D1. |
| D16 | MWS-CFG-1 reads "MUST NOT start with writes enabled" where the design's first sentence said the unrecognized value "stops the server". Stopping is the guidance. | A tester cannot tell a recognized value from an unrecognized one that was treated as restrictive. |
| D17 | MWS-IN-4 dropped "it is not a server error"; MWS-RES-4 dropped "compact"; MWS-ATOM-2 states the outcome (nothing remains applied) and leaves the mechanisms to guidance. | Each dropped phrase could not be decided by a test. Result size is measured in Annex A. |
| D18 | The sentence of MWS-SEC-1, and not only its test method, covers error results. | An error result enters the model's context in the same way. |
| D19 | MWS-RETRY-1 is tested black-box (send the create twice, count) where the design said review. | It can be measured. |
| D20 | MWS-CONC-1 has a proxy-assisted procedure for tools that read and write inside one call. | A stale write cannot be staged through such a tool, and the black-box procedure alone would have flagged correct tools. |
| D21 | Two requirements have no published finding of the exact failure and say so in their rationale: MWS-ANN-1 (rests on the schema text) and MWS-RETRY-2 (rests on reasoning and on the MCP re-issue rule). | The change process asks for a public case; the gap is stated and not hidden. |

## Review of the 0.9 text, 14 November 2026

The 0.9 text was reviewed by a second reviewer, working from the text, the design and the published sources and not from the drafter's notes. It reported 13 points that had to be fixed and a further list of smaller ones. The 13 were addressed before the text was put up for the owner's review; D11 to D21 above record the fixes that changed what a requirement says. A second review then found four of the 13 fixes incomplete. They were completed in the review round recorded below. Points left open are listed in the "Review round" section below.

## Review round, 14 November 2026

The 0.9 text and a list of 49 open items were reviewed by an internal review, a second reviewer and three further reviews, all AI-assisted. Where the reviews agreed, or the fix was a plain correction, the change was applied. No requirement was added, removed or split, and no level changed. The count stays at 29 (23 MUST, 6 SHOULD). Where the reviews disagreed, or a change would reopen a founding decision, alter a level or alter the count, the question was left for the owner. The owner's decisions are in the next section.
